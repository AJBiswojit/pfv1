# PHASE 9 — CART, CHECKOUT & ORDER SUCCESS

**The money path, in the design's language, on this application's commerce core.**

Phase 9 adopts the three surfaces a customer actually transacts through — `/cart`,
`/checkout`, `/order-success` — the way Phases 6, 7 and 8 adopted the product page,
the listing and the wishlist: the pages are written in the design's own vocabulary,
reachable only through the existing `?home=aarna` / `VITE_STOREFRONT_HOME=aarna`
switch, and bound to the SAME contexts, services, validators and state machines the
production pages read. Not one rule about money, stock, addresses, delivery,
payment or order state was re-implemented, moved or duplicated.

Phase 9 is a **UI migration**. `backend/**` is untouched by it, `frontend/src/App.jsx`
is untouched, `home-page/**` is untouched, and no dependency was added.

## 2 · Behaviour preserved, and how it is wired

**Everything the three pages do is done by the application.**

| Behaviour | Where it lives now | How it is wired |
| --- | --- | --- |
| Bag lines, quantity, removal, ceiling | `CartContext` | `cart.items` → `BagLine`; `cart.updateCartQuantity(item.id, n)`, `cart.removeFromCart(item.id)`. The ceiling is `item.maximum` when the cart response carries it, else `getMaxQuantity(product)` — the same rule `CartLineItem.jsx` applies; the server re-checks at placement |
| Move to wishlist | `ShoppingContext.moveToWishlist` | the same action production's bag and the ported wishlist call |
| Offers | `CartContext.applyCoupon` / `removeCoupon` / `couponLapsed` / `priced` | the design's own field; the answer shown is the answer the context returned — never a fabricated acceptance, and a lapsed offer says so |
| Ledger | `cart.totals` | the server's own figures for a signed-in customer, the client presentation calculation for a guest (which the server re-prices at placement). `BagTotals` prints them; nothing is summed on a page |
| A line's own total | `lineTotalFor(item)` — exported once from `Cart.jsx` | `item.lineTotal` when present, else `price × quantity` — the rule `CartLineItem.jsx` uses. One definition, used by the bag, the journey summary and the review |
| Recommendations rail | `useRecommendations({ placement: "cart", cartIds })` + `useProductCovers` + `normalizeMediaReference` + `toDesignProduct` | the application's recommender and media resolver; an empty answer draws no rail |
| Empty / loading / error states | `cart.items`, `cart.isLoading`, `cart.error`, `cart.errorStatus` | in the production bag's own order of precedence; `Try Again` → `cart.refreshCart()` |
| Checkout steps | `CHECKOUT_STEPS` + `CheckoutContext` | the rail is drawn **from `CHECKOUT_STEPS`** (`STEP_LABELS` only supplies the words), so the rail can never drift from the journey the context runs; a step ahead is `disabled` |
| Customer validation | `validateCustomer` (`utils/checkout.js`) | the step's primary button validates, focuses the first invalid field, and refuses to advance |
| Address | `AccountContext.addresses` + `account.addAddress` via the production `AddressModal`; `checkout.selectAccountAddress(id)` / `selectAccountAddress(id, snapshot)`; `checkout.setGuestAddress`; `validateAddress`; `formatPhone` | ownership and validation stay the account's and the application's |
| Delivery | `DELIVERY_METHODS`, `calculateDeliveryFee`, `readShippingRules()`, `getDeliveryEstimate` + `formatDeliveryEstimate` | fees, the complimentary threshold and the real date ranges come from the application's matrix and rules |
| Payment | `PAYMENT_METHODS`, `checkout.setPaymentMethod`, `checkout.startPayment()`, `paymentRef.current.pay()` | a method must be chosen first; the page collects **no** instrument (the gateway's hosted window does) — asserted: no `cvv`/`cardNumber`/`upiId` in the source, no `type="password"` in the markup |
| Payment states | `PAYMENT_STATUS.PENDING` / `FAILURE` / `CANCELLED` + `checkout.retryPayment` / `resetPayment` / `paymentStatus` | PENDING panel while the gateway decides; FAILURE with Try Again / Change Method / Return to Bag; CANCELLED with its own way back. No success is invented |
| Order placed | `checkout.completedOrder` → `navigate("/order-success", { replace: true })` | the ONLY thing that moves the journey forward is the server's confirmed order |
| Bag cleared | **`CheckoutContext` only** | asserted three ways: `clearCart` appears in neither page nor the confirmation, and the context's own clear sits behind the confirmed order. The bag is never cleared before the server confirms |
| Bag-changed guard | `checkout.bagChanged` → `checkout.goToStep(2)` | a bag edited mid-journey returns to the review with the notice |
| Idempotency | `newAttemptId` / `attemptId` (in `CheckoutContext`, via `utils/checkout.js`) | untouched, and not re-implemented on the page |
| Confirmation | `OrderContext.currentOrder` + `config/orderConfig.getPaymentStatus` | order number, date, payment method and status label, delivery level, pieces, address and the pricing breakdown all come from the order; **no delivery date is claimed** (the atelier has not scheduled one at placement) and no carrier or consignment is invented |
| Ways onward | `/account/orders/:id`, `/account/orders/:id/track`, `/shop`; guests → `/signup?returnTo=%2Faccount%2Forders` | the application's existing routes, exactly as production links them |
| Direct visit with no order | the honest empty state | "We couldn't find that order." — a confirmation is a page reached through its own transaction, not a URL |

**New chrome, drawn only where the design is silent.** `aarna.checkout.css` carries
*only* what the design never drew — it has no bag **page**, no checkout **journey** and
no **confirmation** — and every declaration is scoped to `.aan-root` with a design token
for its value. The port's parity gate counts the design's seven sheets (55 files /
88,885 B), not this file. The rules the design *does* have are used as they are:
`.container`, `.crumbs`, `.label`, `.display`, `.qty`, the `.btn` register,
`.totals`/`.totals__disc`/`.totals__grand`/`.totals__note`, `.promo-form`/`-.applied`,
`.checkout__lines` (the four-cell line grid the checkout prototype drew), `.empty`.

Two things worth naming, because they were decisions rather than accidents:

* **The announcement rail and the footer are the design's own chrome** and they travel
  with `/cart`. On the order journey the frame keeps the **footer** — production's own
  layout keeps `SiteFooter` on the money path too (`layouts/CustomerLayout.jsx:117 → 147`)
  — and drops the rail, the mega menu, the search overlay and the drawer.
* **The "Secure Checkout" note is hidden below 600px** and the Bag control keeps its
  live count from `useCart()`; the 600px width is a literal the design itself uses
  (`home-page/src/styles/layout.css:15`).

### Two defects the browser pass found and this phase fixed

1. **A line's own figure rendered ₹0 for a guest bag.** The cart response carries
   `lineTotal` for a signed-in customer; a guest bag has no such field, and the journey

   exactly once and that no line renders a zero.

   flex column, so on the journey's wider form the field's text and its mark became two
   flex items. Fixed by wrapping label + mark in one `.pf-lab` span and stating the
   design's own label rule for the form (a label is a column of fields). Measured after the
   fix: label height 97.2px → 73.6px, the mark on the label's own line.

A third, found by SSR inspection before the browser pass: the signed-out branch of the
customer step advertised "No account needed" and linked `/signin?return=/checkout`, which
both contradicted the guard and carried a stale parameter name. The page never renders for
a signed-out visitor, but the branch is written honestly now — "Signed out" /
"Sign in to continue" with `returnTo=%2Fcheckout`.

Also corrected while measuring: the journey summary originally repeated the quantity
(`× 2` next to "Qty 2"). The design's line is a four-cell grid, so the third cell is an
empty spacer and the figure stays flush right where the design put it.

## 5 · Limitations, unverified work and known gaps

**Not verified, and not claimed:**

* **No live backend, no order was placed, no payment was made.** The sandbox has no
  backend (and no Postgres/Redis), so nothing in this phase is an end-to-end money-path
  verification. The order-creation call, the Razorpay window, the payment webhook and the
  order-confirmation read were **not** executed.
* **Consequently unrendered with real data**: the confirmation with a confirmed order
  (source-pinned: the layout, the status register, the order's own pricing, the routes,
  the guest claim flow), and the delivery / review / payment steps beyond step 2 (the
  first two steps WERE exercised in a real browser; steps 3–4 need a session, since step 2
  requires an address, which is a signed-in account's). Their source-level contracts are
  pinned by tests.
* **`PAYMENT_STATUS.PENDING` / `FAILURE` / `CANCELLED` panels are pinned at the source
  level only** — each needs a live gateway answer or a webhook to appear.
* **No signed-in session was ever reached.** `AuthContext` validates a stored token
  against the API, and there is no API; the authenticated branches of the bag
  (`item.maximum`, server totals, server coupon), the account's addresses and the
  `selectAccountAddress` path are therefore pinned by tests over the real contexts, not
  exercised in a browser.
* **The harness readings are harness readings.** They mount the pages; they are not a
  route.
* **All catalogue-populated browser readings are fixture readings** (Phase 6/7 fixture
  products `PF-P6-*`, fixture plates). No fixture was written for this phase.
* **The 21 pre-existing `npm test` failures are unchanged** — the baseline reproduces
  exactly (434 = 412/21/1), and none of them is in a Phase 9 surface.
* **`WishlistContext.unavailable` remains flagged** (carried over deliberately), and the
  wishlist add-to-bag drawer behaviour is untouched.

**Deliberate divergences, reported rather than hidden:**

* The small-screen action bar on `/checkout` **follows the reader** (sticky) instead of
  being pinned to the viewport as production's is; the in-flow Back / Continue pair stays
  under the step. The bar carries the bag's total, which is what production's bar does.
* `/cart` keeps the design's full shell even on mobile, where production has its own
  compact bar; the bag's bar shows the total and links to the checkout.
* `document.title` is set by the two pages from an effect — client-only, with the previous
  title restored on the way out (production does the same).

**Housekeeping:** the browser kit's dependency tree (86 packages, ~111 MB) was removed
after the run — the probe, the harness and the evidence stay, and the kit is restored with
two commands (below). `.p9/evidence/` holds the 64-reading JSON and five PNGs. The port
tool's `ADDED` block documents the five added modules.

## 6 · Git status, and `home-page/` untouched

**Nothing was staged, nothing was committed, and no branch operation was performed in this

### The branch repair this phase sits on

Phase 9's work is built on a branch whose history had been lost and then repaired, with
explicit approval, before this phase began:

* The branch was found re-created at `10890db` (Phase 2D) with the Phase 3–8 commits gone.
  Four commits were recorded as lost and unrecoverable — P6 `4311209`, P7 `a03694b`,
  A `3f15103`, B `5e83257`; none of them had ever been pushed, so nothing on the remote
  could bring them back, and reconstructing them by guessing was rejected.
* The approved repair was **`git reset --mixed 1d64755`** — `1d64755` being the branch's own
  remote tip (`origin/arena/649fd845-pfv1`), i.e. the furthest point the remote could prove.
  `--mixed` moves `HEAD` only: not one working-tree byte was discarded, and this phase's own
  fixes were already on disk when it ran.
* The repair was verified rather than assumed: a full-tree manifest (1,838 files, sha1 +
  size each) taken before and after the reset is **byte-identical**
  (manifest sha256 `e19051c4440cfe5339c5f8b9b5da5d50539176ad7ccddc010d36e715370f52e9`), and the
  working-tree content of the four Phase 3–8 commit (entry-point files) was confirmed present.
