### Deliberate behaviour choices (each with a reason)

| Choice | Why |
|---|---|
| The empty state says *"saved to your account when you are signed in, and on this device when you are not"* | The design said "saved on this device", which is false for a signed-in customer. The port states both cases and claims neither |
| A saved id whose record is missing shows **"No longer available"** with the production page's own sentence | `WishlistContext.unavailable` did not become true within 12 s in either the guest or the fixture probe, while the production page states this much for any missing record. The port mirrors the application rather than promising a resolution that may not arrive (see §7, finding 2) |
| The add-to-bag confirmation is an inline note that clears after 4.2 s, and the design's bag drawer opens | The production page opens the mini-cart and clears its feedback after 4.2 s; the port opens the design's own drawer and keeps the same timing |
| The card's plates are converted from media records to URLs | The design's card draws URL strings; `useProductCovers` rows carry `{id, src, …}` records. Without the conversion every card shows `src="[object Object]"` — see §7, finding 1. **Both** ported surfaces now do this through the application's one resolver, `normalizeMediaReference`; the wishlist's local `plateUrl` helper is gone |
| `/wishlist` redirects **inside** the port | So a customer following the header's heart from a ported page never sees the production chrome paint first |

## 6 · Risks and limitations

1. **No live backend.** Every catalogue-backed reading is fixture-driven. The wishlist's
   authenticated path (server `GET/POST/DELETE /wishlist`, the 401/403 surface) is pinned in code and
   asserted at the source level but **not** exercised against a server. The 401/403 wording and the
   sign-in `returnTo` link are unproven end-to-end.
2. **The dev query parameter is per page load** (§4). A reviewer navigating by clicking rather than
   by URL will leave the port unless the environment switch is used.
3. **Dev-only module preloading.** With the switch off, Vite still serves the port's modules in
   development (a static import in `CustomerLayout`, Phase 2D's design). The production build is a
   single bundle, so it carries the port's code whether or not the switch is on — unchanged from
   Phases 2D–7, and outside this phase's scope.
4. **`/collections` has no customer-facing scope** without a catalogue (audit U1); the wishlist's
   empty-state CTA therefore targets `/shop`, which always resolves.
5. **`/pages/<slug>` and `/track-order`** (the design's vocabulary) are answered by the customer 404
   with the switch on, as the audit decided; no redirect was invented for them.

## 7 · Findings: the Phase 7 regression (fixed in this pass) and one application behaviour (flagged)

**Finding 1 — Phase 7's listing cards rendered no image. FIXED in this pass.** `pages/Shop.jsx` spreads
`useProductCovers` rows into the design's card (`plates = [row.image, row.hoverImage]`), but those
are media *records* (`{id, src, …}`) while the design's `ProductCard` draws `product.images[0]` as a
URL. Result: `src="[object Object]"`, the image failed to load, and the card's own `onError` hid it —
so every card on `/shop` rendered without a plate. Measured in the probe (`fixture`): 12 of 12 cards,
12 of 12 broken. Phase 7's probe never asserted an image `src`, which is why it passed at the time.
The Phase 8 wishlist page never had this defect — it converted its plate to a URL, and its card's
cover loaded in the first probe too.

*Fixed* by converting both plates with the application's **own single media resolver**,
`normalizeMediaReference` (`services/media/mediaPaths.js`) — the same function every production image
already goes through (`components/PratikshyaImage`, the design-system card, the wishlist button). The
edit is in `SHOP_EDITS` of `frontend/scripts/aarna-port.js`, i.e. **in the tool, not in its output**:
`pages/Shop.jsx` is regenerated by `--copy` and `--check` still exits 0, so the port is reproducible.
No fixture URL was hardcoded and no second image-resolution path was introduced.

The wishlist page had solved the same problem with a local `plateUrl` helper; that helper is now
**gone** and the page uses the same one resolver, so the port has one image-resolution path instead of
two. Its rendered plates were re-measured in the same browser pass (§5): 2/2 valid, 0
`[object Object]`, 2/2 loaded.

*Verified:* `--copy` and `--check` exit 0 (55 files, pins `Shop.jsx 44` / `Wishlist.jsx 9` /
`Info.jsx 11` unchanged — the pins count design lines the port differs on, so a regenerated page
cannot drift); two regression tests (§3); the whole battery re-run (§3); and the browser probe re-run
at desktop **and** mobile (§5) — **12/12 valid `src`, 0 `[object Object]`, 12/12 loaded at both
widths**, against 0/12 before.

**Finding 1b — the same defect class, checked everywhere else.** `useProductCovers` is called on
exactly two ported surfaces (`pages/Shop.jsx`, `pages/Wishlist.jsx`); both now resolve through
`normalizeMediaReference`, and the regression tests pin both. The design's other card consumer
(`home-page/`, untouched) and the production surfaces are unchanged.

*Note on provenance:* `pages/Shop.jsx` is Phase 7's committed file, so the working tree now differs
from commit `a03694b` by these eight lines. Nothing was amended or rewritten: the correction is
carried by its own commit, staged from exactly three paths (`pages/Shop.jsx` whole; the `SHOP_EDITS`
hunks of `scripts/aarna-port.js`; the regression-test hunk of `aarnaListingPage.test.js`) and placed
immediately before the Phase 8 commit — see `/home/user/PHASE-8-COMMIT-PLAN.md`.

**Finding 2 (flagged, not fixed) — `WishlistContext.unavailable` does not become true.** A saved id the catalogue cannot
resolve is looked up (two `404 /api/v1/products/…` responses recorded), but the `unavailable` flag
stays false and the id is never retried (`attempted.current` is marked while the effect's cleanup
cancels the in-flight resolution when the catalogue emits). The production wishlist hides this
because it states "No longer available" for any missing record; the Phase 8 page does the same. The
context is application code outside this phase's scope, and its UI consequence is not observable
today.

*Not fixed* — it is a Phase 8 audit-era application behaviour, not a port behaviour.
**Flagged for a future phase.**
